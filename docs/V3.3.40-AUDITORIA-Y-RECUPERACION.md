# V3.3.40 — Auditoría general y procedimientos de recuperación

**Ámbito:** RedLibertad, `main` desde V3.3.39, Node.js, PostgreSQL 18, multimedia local y PWA. No se han ejecutado copias, restauraciones, cambios de permisos ni acciones destructivas sobre producción con esta auditoría.

## Resultados comprobables en el repositorio

| Área | Evidencia / decisión |
| --- | --- |
| GitHub y despliegue | GitHub Actions comprueba JavaScript y PostgreSQL 18. El verificador de producción coteja `/api/health`, `/api/public-config` y `/api/ready` con el commit esperado. Esto no demuestra que se puedan restaurar copias. |
| Autorización | `src/middleware/auth.js` consulta el estado real de la cuenta y la versión del token antes de autorizar; el router de mensajes exige autenticación. No se modifica el modelo de permisos. |
| Compartir publicaciones | `/p/:id` exigía contenido publicado y audiencia pública, pero permitía mostrar el texto en una página pública cuando `content_level` era restringido. Se corrige en esta versión. |
| URLs inválidas | Identificadores de publicación no numéricos o fuera del rango BIGINT podían provocar fallos SQL y HTTP 500. Se rechazan con 404 sin consultar la base. |
| Caché PWA | `public/sw.js` excluye API, uploads, páginas de publicaciones, admin y multimedia; solo guarda shells y archivos estáticos. Sin cambios en esta versión. |
| SEO/privacidad | La indexación de perfiles, publicaciones y Reels ya tiene filtros públicos. Se conservan; los posts restringidos mantienen `noindex` y cabecera privada sin exponer captions. |
| Infraestructura | `DEPLOY-COOLIFY.md` identifica `/data/uploads` como directorio persistente recomendado, pero no hay prueba en GitHub de backups automáticos/restauraciones recientes. Se mantiene como pendiente de verificación de operaciones. |

### Verificaciones pendientes fuera de GitHub

- **Coolify:** confirmar programación real, estado y retención de backups de PostgreSQL 18 y volúmenes persistentes; revisar logs de errores y espacio libre.
- **Restauración:** ejecutar prueba de restauración en **entorno aislado**, nunca sobre la base o el volumen en producción; verificar tablas, relaciones y acceso a varias imágenes y vídeos con permisos correctos.
- **Correo y notificaciones:** comprobar que las preferencias y el consentimiento reales se respetan; no enviar campañas masivas de prueba.
- **Experiencia:** comprobar manualmente inicio, login, publicar, comentar, chat, bloquear, notificaciones y PWA en Android, iOS y escritorio con cuentas de prueba propias.
- **Indexación real:** consultar Google Search Console; el sitemap válido no confirma por sí solo que Google haya indexado las páginas.
- **Datos multimedia privados:** revisar el modelo de acceso a archivos compartidos por URL, particularmente adjuntos de conversaciones. No cambiar la infraestructura ni revocar URLs sin un plan compatible.

## Recuperación y copia de seguridad — lista operativa

1. Identificar en Coolify el proyecto, servicio PostgreSQL 18 y volumen de `UPLOAD_DIR` que estén **realmente en uso**, sin publicar credenciales ni copiar variables secretas al repositorio.
2. Comprobar que las copias de **PostgreSQL** son periódicas, cifradas, con retención y ubicación independientes del VPS. Guardar fecha, tamaño y resultado del último backup en un registro privado.
3. Comprobar que las copias del volumen multimedia `/data/uploads` incluyen imágenes, vídeos y las rutas de medios utilizadas por la base. Preferir snapshots consistentes o una ventana coordinada de backups para evitar referencias a archivos que aún no se copiaron.
4. Con una copia de la base creada fuera de producción y sin credenciales expuestas, validar la estructura del archivo mediante `pg_restore --list archivo.dump` cuando el backup sea de formato custom. **Esta inspección no constituye una restauración satisfactoria.**
5. Restaurar base y archivos **solo en un entorno aislado** con datos protegidos, credenciales separadas y sin correos/push reales. Comprobar esquema, conteos orientativos, permisos, referencias multimedia y `/api/ready`.
6. Registrar fecha, responsable, duración, incidencias y commit utilizado; calcular objetivos de pérdida máxima de datos (RPO) y tiempo de recuperación (RTO) **a partir de pruebas**, no de suposiciones.
7. Si producción falla tras una fusión, suspender nuevas versiones, revisar el commit desplegado y los logs de Coolify; preferir volver al último artefacto estable. **No** restaurar PostgreSQL ni reemplazar archivos sin confirmar que el fallo requiera recuperar datos: un rollback de código y un rollback de datos son operaciones distintas.

**Criterio de cierre:** CI y despliegue en verde son obligatorios para fusionar; la resiliencia ante pérdida de datos permanece **no verificada** hasta superar al menos una restauración aislada de PostgreSQL y multimedia. No se afirma aquí que existan backups operativos configurados.
