# RedLibertad V3.2.110 — Bloqueo de instantáneas concurrentes Stripe TEST

## Problema
La V3.2.109 protegía la sincronización manual ante webhooks (con `last_event_created`) y suscripciones canceladas. Dos sincronizaciones **manuales** simultáneas, sin un nuevo webhook, leen la misma marca `last_event_created` y podían sobrescribir sus resultados: la respuesta remota más antigua podía ganar al escribir la última.

## Corrección limitada
- La lectura de la suscripción de laboratorio incluye `xmin::text AS row_version`, identificador de versión MVCC propio de PostgreSQL.
- El `UPDATE` exige tanto la identidad y `last_event_created` anteriores como `xmin::text=$10`.
- Cuando otro proceso ya ha modificado la fila, el segundo escritor recibe HTTP 409 `stripe_test_sync_conflict` sin cambios. La UI móvil ya ofrece reintentar después de actualizar (V3.2.109).
- Sin nuevas tablas, variables, migraciones o llamadas adicionales a Stripe.

## Validaciones
- `npm run test:marketplace-stripe-sync-row`: fila versionada, error 409, aislamiento de permisos y facturación.
- GitHub Actions / PostgreSQL 18: dos reconciliaciones manuales de una misma suscripción TEST; se retiene el estado más reciente aunque `last_event_created` no cambie.
- Siguen pasando las suites históricas de identidad, webhook, cancelación y concurrencia V3.2.109.

## Restricciones y riesgos
Esta mejora solo toca `marketplace_stripe_test_subscriptions`. Stripe LIVE y la contratación siguen bloqueados; no modifica facturación, IVA, cuotas, políticas, permisos reales, productos, fotos, WooCommerce, enlaces externos de compra ni el piloto gratuito MundoTaza.

El token `xmin` es una protección optimista local de PostgreSQL, no una secuencia de eventos Stripe ni un mecanismo de conciliación financiera. Revisar la estrategia de versionado y la idempotencia integral antes de estudiar habilitar cobros reales.
