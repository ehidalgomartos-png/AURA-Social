# RedLibertad V3.2.108 — Checkout Stripe TEST atómico y selección estable

**Base:** V3.2.107 `c22786ca2103b885cc1143c8bd5aa29ee087bcbc`. Alcance exclusivo al laboratorio de pruebas de Stripe.

## Incidencia revisada
Hasta esta versión dos peticiones concurrentes para un mismo vendedor podían leer `no hay Checkout pendiente` y crear ambas una sesión remota antes de insertar la fila local. La comprobación de sesiones pendientes evitaba los intentos secuenciales, pero **no cerraba la carrera simultánea**.

## Corrección técnica
- `createTestCheckout` utiliza un **cliente dedicado de PostgreSQL** y una transacción `BEGIN/COMMIT` con `pg_try_advisory_xact_lock` por identidad de vendedor (prefijo propio del laboratorio).
- Un segundo intento del **mismo vendedor** durante la primera operación recibe inmediatamente `409 stripe_test_checkout_in_progress` **sin contactar con Stripe**, ni esperar indefinidamente por una conexión transaccional ocupada.
- Los vendedores distintos pueden ejecutar simulaciones independientes, sin bloquearse entre ellos.
- Las comprobaciones de suscripción cancelada, Checkout anterior verificado y sesión creada aún pendiente se hacen con el bloqueo adquirido, antes del llamado externo.
- El servidor solo responde con una URL de Stripe TEST si la sesión está validada y su fila local se ha insertado correctamente; el registro se **confirma (COMMIT) antes de responder**.
- Si falla el API de pruebas, la validación de la sesión o el INSERT de persistencia, se ejecuta `ROLLBACK` y se libera el cliente PostgreSQL incluso ante errores. No se modifican las suscripciones comerciales.
- El navegador conserva la opción Profesional/Profesional Plus seleccionada cuando recarga el estado del laboratorio. Cambia la versión de caché del script para distribuir la corrección.

**Límite explícito:** una pérdida de conexión entre crear una sesión remota TEST y confirmar el commit puede dejar una sesión remota de prueba huérfana. Este cambio resuelve la duplicación por carrera local, pero **no promete entrega exactamente una vez** ante fallos del proveedor. Es un riesgo que habrá que cubrir por separado antes de un eventual sistema LIVE.

## Pruebas
- `npm run test:marketplace-stripe-checkout-atomic`: rechazo de intento simultáneo sin petición saliente, COMMIT previo al éxito, ROLLBACK al fallar Stripe o persistencia, validación de vendedor, preservación del plan elegido y guardas LIVE.
- `tests/marketplace-stripe-reenrollment-postgres-v32102.test.js`: integración real con servicio temporal **PostgreSQL 18** (solo `127.0.0.1`) que retiene abierta la petición del primer vendedor, rechaza una simultánea para el mismo usuario y verifica que otro vendedor sí puede operar. Tras confirmar la primera, un tercer intento queda bloqueado por la sesión pendiente, con **cero sesiones duplicadas**.
- Se mantienen las pruebas previas de Checkout, webhooks, renovaciones/cancelaciones, historial, privacidad y WooCommerce.

## Protecciones
- Solo tablas `marketplace_stripe_test_*` y API TEST del laboratorio. Sigue prohibido aceptar claves `sk_live_` o eventos `livemode=true`.
- No se crean nuevas variables, formularios fiscales, tarifas definitivas o contratos.
- **Facturación aparcada** tal como se acordó. Stripe LIVE, pagos reales y permisos profesionales comerciales continúan desactivados. No se interfiere con la compra externa de productos ni el piloto gratuito de MundoTaza.
- La fusión exige CI verde y después comprobación read-only del commit de Coolify.

## Verificación visual sin cargos de prueba
Como administrador, abrir `/marketplace/suscripciones/laboratorio`, actualizar y comprobar que el plan seleccionado se mantiene mientras el laboratorio refresca. **No hace falta crear otra sesión de pago de prueba para validar esta corrección**; el test PostgreSQL cubre específicamente la concurrencia.
