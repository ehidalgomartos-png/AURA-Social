# RedLibertad V3.2.109 — Reconciliación Stripe TEST protegida ante webhooks concurrentes

## Problema reproducible
La sincronización manual del laboratorio consultaba una suscripción en PostgreSQL, recuperaba el estado remoto y lo escribía sin comprobar si, durante la llamada a Stripe, un webhook firmado había avanzado el estado local. Una cancelación podía ser sobrescrita por una respuesta remota anterior.

## Solución
- La consulta local incluye `last_event_created`, que se utiliza como versión optimista.
- El `UPDATE` manual exige que el identificador de vendedor, plan, suscripción, cliente y versión de evento no hayan cambiado desde la lectura. Si cambian, devuelve HTTP 409 `stripe_test_sync_conflict` y **no escribe**.
- Una suscripción que ya está `canceled` no puede volver a `active`/`past_due` por una sincronización manual, aunque la versión de evento no haya cambiado.
- El laboratorio explica el conflicto en español y ofrece volver a consultar. No crea sesiones ni realiza cobros.

## Verificación
- `npm run test:marketplace-stripe-sync-race`: pruebas unitarias de compare-and-swap, rechazo de identidad, límites TEST y texto móvil.
- PostgreSQL 18 en GitHub Actions: webhook de cancelación ejecutado durante el fetch remoto; se verifica que no se revierte, que el conflicto devuelve 409 y que una sincronización estable sí funciona.
- No hay migraciones ni variables nuevas; los eventos siguen auditados por el mecanismo anterior.

## Restricciones
Stripe LIVE, facturación real, contratación pública, precios definitivos y permisos por plan permanecen desactivados. No se alteran productos, WooCommerce, fotos, enlaces de compra externa ni el piloto gratuito MundoTaza.

## Riesgo residual
El bloqueo optimista impide sobrescribir webhooks que ya han actualizado la versión local. No sustituye una reconciliación de eventos remotos con marca temporal y verificación completa cuando exista facturación real; requiere diseño y revisión independientes antes de habilitar Stripe LIVE.
